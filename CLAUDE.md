# HOAForecaster

The specification is [HOAForecaster_REQUIREMENTS.md](HOAForecaster_REQUIREMENTS.md). Read it before changing behaviour; cite its section numbers in reviews and commit bodies.

## Public code, private data

This repository is public. Never commit a real association's name, figures, people, documents or workbook – not in code, tests, fixtures, comments, commit messages or docs. Real data lives in the private sibling repository `HOAForecaster-data` (section 8.1). Public tests use the fictional demo project in `demo/`.

## Layout

- `src/hoa_engine/` – the calculation engine (section 6). Pure Python, no I/O, `Decimal` throughout. `run(scenario)` is the only entry point – a scenario carries its own `Facts`. `model.py` also holds `Project` and the JSON project format; `upgrade.py` turns schema 1 and 2 files into schema 3.
- `src/hoa_workbook/` – Excel export and re-import (sections 7.1, 7.6). `layout.py` is the single source for sheet names, rows and labels, shared by `export.py` (writer) and `read.py` (reader); `charts.py` builds the native charts. It imports only `hoa_engine.model` and `hoa_engine.validate` – never the engine – so its formulas stay an independent check on the engine (enforced by `tests/workbook/test_independence.py`).
- `src/hoa_store/` – project storage (section 8): one JSON file per project in the data folder, trash, export/import of project files, first-run demo seeding. Every error is a `StoreError` with a plain-language message.
- `src/hoa_app/` – the local server (sections 7, 8, 10.1). `api.py` is the FastAPI app – the JSON API under `/api/` and the built front end from `web/dist`; `__main__.py` is the `hoaforecaster` launcher; `lock.py` keeps one app per data folder.
- `web/` – the screens (section 7), Vite + React + TypeScript, built into `web/dist` and served by `hoa_app`. `src/api.ts` is the only code that talks to the server; `src/decimal.ts` keeps money as exact decimal strings (numbers only for display and charts); `src/pages/` are the screens – `ScenarioScreens.tsx` is a scenario's layout (one form, autosave, live results, copying) and its six screens; `src/App.tsx` exports the `routes`; `src/scale.ts` mirrors `charts.py`'s shared grid. Tests – `npm test` (logic, components, and the app's own routes driven against a mocked API).
- `tests/engine/` – unit tests and the section 9 acceptance tests; 100% coverage of `hoa_engine` is enforced. `tests/workbook/` – export recalculates in LibreOffice to the engine's figures, export → import round trip, Excel open check (Windows with Excel), bad-file handling. `tests/store/` – storage, including concurrent saves and hostile files. `tests/compare.py` – the engine-vs-workbook comparison.
- `demo/fixtures/` – the fictional project (`project.json`), its exported workbook (`reference.xlsx`) and the figures LibreOffice computed from it (`expected.json`). Regenerate with `uv run python demo/build_reference_workbook.py` after changing the demo project or the exporter's formulas; `expected.json` changing means a formula changed.
- `tools/recalc.py` – LibreOffice headless recalculation and formula-error scan. `tools/extract_expected.py` – reads expected figures out of any workbook in the reference layout. `tools/excel_check.ps1` – opens a workbook in real Excel and reports any repair.

## Commands

```
uv sync                                     # install
uv run hoaforecaster                        # start the app – builds web/dist with npm first if it is missing
uv run pytest --cov                         # tests; add HOA_PRIVATE_DIR=../HOAForecaster-data for the private set
uv run ruff check . && uv run ruff format --check .
uv run mypy
cd web && npm ci                            # front-end packages (exact pins, lockfile)
cd web && npm test && npm run lint && npx tsc --noEmit
cd web && npm run build                     # after changing web/src – a running server lists dist files at start-up, so restart it
```

`git config core.hooksPath .githooks` once per clone turns on the pre-commit checks – the real-data guard (deny-list at `../HOAForecaster-data/denylist.txt`, or `$HOA_PRIVATE_DIR`), ruff, mypy, and the front end's types, lint and tests.

## Stack decisions

- Python FastAPI backend + React/TypeScript front end (section 11, decided in v1.2). Engine and Excel exporter are both Python.
- `uv` for the Python environment; Python ≥ 3.12.
- Money and rates are `Decimal` in memory and decimal strings in JSON; floats are refused on load.
- Dues rounding applies only to grown dues, each year rounded half-up from the unrounded growth; typed and pinned values are used as typed.
- Expected figures always come from a spreadsheet recalculated by Excel or LibreOffice, never from the engine.
- Export – sheets in the order Method, Project (the association's name and notes), Compare, Charts, then one per scenario. Scenario sheets are named from the scenario, cleaned to a legal, unique name (31 UTF-16 units, no trailing apostrophe); the full name is in cell A1. Dues settings sit below the table; the rounding cell drives the dues formulas (a dropdown), while the dues mode is set in the app because it decides which cells hold formulas. Special assessments are a list, one row each with spare rows, summed into the year row by SUMIF – so installments and notes survive a re-import. Exporting a scenario with problems is refused, naming it.
- User text is always written as text, and text starting with = + - @ also gets Excel's quote prefix so it stays text when edited or saved as CSV. Control characters (other than tab, newline and return) are refused in every text field when a project is read.
- Import (`read.py`) reads only the export layout; a workbook in the layout before v1.6 (Inputs and Expenses sheets, no Project sheet) is refused with a plain message – its project file still imports. Section 7.1a (CSV of expenses and FFB) and 7.1b (the original reference workbook, with its partial first year) are still open; the private repo's `fixtures/make_project.py` does 7.1b as a one-off. A re-import is identical to the exported project except that numbers pass through Excel's doubles (about 15 significant digits). Each label is looked for only in its own part of a sheet (Plan rows from the top, the scenario's blocks each below the one before, totals as the last row with the label), so an expense or note worded like a label never stands in for it. Start and end years are checked as soon as they are read, before any year is walked. An expense row without its year formulas is refused rather than read, because the sheet's own totals would leave it out; a formula typed over a fact or Fully Funded Balance figure is refused.
- Import limits – 20 MB file, 20 MB unpacked, 100:1 compression per part, 2,000 rows by 200 columns per sheet; defusedxml must be active. Imported projects are validated before they are returned. A project holds at most 200 scenarios; the schema 2 upgrade refuses more than 1,000 baseline lines or line changes, and more than 50,000 lines written in all (each scenario gets its own copy of the baseline's – a small crafted file must not grow into a huge one). Project files and workbooks are parsed off the server's event loop.
- Two environment variables, never interchangeable – `HOA_DATA_DIR` is the app's own data folder (default the per-user application data folder, `%APPDATA%\HOAForecaster` on Windows); `HOA_PRIVATE_DIR` is the private data repository, used only by the private acceptance tests and the commit guard. The spec's "bundled demo folder" default became the app data folder with the demo copied in on first run, so the app never writes into the repo.
- Storage – `<data>/projects/<id>.json` and `<data>/trash/<id>.json`. Ids are 12 hex characters made by the server; user text never becomes a file name. Saves are atomic, serialised by a lock and carry a `revision`; a save names the revision it started from and is refused if another save came first. There are no drafts – every edit is saved as it is made (spec 7.2); a `drafts` folder left by an older version is ignored. Delete moves to the trash folder (no restore in the app yet). The demo is copied in only when the projects folder does not yet exist, so a deleted demo stays deleted.
- Timestamps – the project and each scenario have created and modified times (spec section 3). A scenario is identified by its name; a save that swaps exactly one name for another is a rename and keeps that scenario's history, while two renames in one save start new histories. Export project carries the timestamps, not the id or revision, and its import keeps valid ones; the Excel workbook carries no timestamps, so a re-imported workbook starts new ones.
- Server – binds to 127.0.0.1 only (the launcher has no host option). Every `/api/` call must carry the per-launch token in `X-HOA-Token`; the token is generated at start-up and written into `index.html` as it is served (placeholder `__HOA_TOKEN__`), so other web pages cannot call the API (CSRF). The Host header must be `127.0.0.1` or `localhost` (DNS rebinding). Bodies are capped at 21 MB before they are read, and JSON bodies are refused over 5 MB. Front-end files are served only from a list made at start-up – request text never reaches the file system. The page itself is never cached. Uploads are read in memory, never spooled to the temp folder. Errors are `{"message", "problems"}` in plain language; nothing returns a traceback. The front end gets a strict Content-Security-Policy.
- Restarting (the header's Restart button) – `uv run hoaforecaster` is a small supervisor that runs the server as a child process (`--serve`, hidden). `POST /api/restart` (token-guarded) answers first, then stops that server, which exits with code 75 – or ends itself after 5 seconds if it has not stopped. The supervisor starts a new server only once the old process has ended and the port is free (it waits up to 10 seconds, then gives up rather than start a second server), rebuilding the screens first if they changed; the browser opens only on the first start, and the page waits for a page carrying a new token before it reloads. Without the supervisor (tests, `--serve`), `/api/about` says `can_restart: false` and the button is hidden.
- Starting again while running – the running copy is its launcher (the supervisor), not only its server. For its whole life the launcher holds `<data>/.launcher.lock` and keeps `<data>/.running.json` (its pid, port and a stop key of its own; written whole through a new file opened exclusively, never following a link; at most 4 KB is ever read back, and anything damaged, nested or out of range is no record) – removed when it ends, only if still its own. Each server it starts gets the key through its stdin (`--stop-key-on-stdin`), never its command line. A new launch that cannot take the launcher lock posts the key to `POST /api/stop` on 127.0.0.1 – through an opener with proxies off and redirects refused, so neither a proxy nor a redirect ever carries the key – asking again for up to 2 minutes while that copy is still building or between servers. The guard checks the stop key, never the page token, so nothing the page runs can stop the server; `create_app` takes the key and the stop action together or neither. The old server answers, stops (stopping for good wins over a restart asked at the same moment), and ends itself after 5 seconds if it has not; its launcher then exits 0. The new launch waits up to 15 seconds for the launcher lock and the old port, then starts as usual – or says the running copy could not be stopped and starts nothing beside it. Ctrl+C while waiting ends quietly. If the record cannot be written the app still starts and says a relaunch will not stop it. A copy started before this version holds no launcher lock and cannot be stopped this way. `HOAForecaster.bat` pauses only when the app stopped with a non-zero code, so a replaced copy's window closes.
- Problems are plain sentences that name the field in words ("the 2031 expense 'Gate' cannot be negative"); the editors show them as a list. Field keys for highlighting the exact input are a possible later change to `validate.py`.
- New projects and scenarios – `POST /api/projects` with only a name builds a project with one blank scenario ("First scenario") from the spec's defaults, and `GET /api/blank-scenario?name=` gives a blank scenario for the new-scenario screen (`hoa_app/template.py`), so the defaults live in Python once.
- Dependencies resolve only from releases old enough for a bad one to be caught – Python a week (`[tool.uv] exclude-newer`), npm two weeks. npm has no rolling setting, so the front end's exact pins and its lockfile are made with `npm install --before=<date two weeks ago>`; do the same whenever packages are added or upgraded.
- Not yet built – trash list and restore, CSV import of the expense and FFB tables (7.1a), importing the original reference workbook from the app (7.1b), choosing the data folder in the app (it is `HOA_DATA_DIR`).
- API results carry money and rates as exact decimal strings; the front end converts to numbers only for display and charts.
- The Charts sheet's shared dollar scale is passed in by the caller from the engine's results, snapped to a grid whose lines coincide with 0–100% in 20% steps.
- Expense lines (spec 4.1) – one list per scenario, each line with a `frequency` (`monthly`, `yearly`, `every`, `once`) and an `id` (`[a-z][a-z0-9_-]{0,39}`, unique in the scenario – lower case and starting with a letter, so a spreadsheet COUNTIF never reads one as a number and two never match by case). New lines get the first free `line-N` among the ids of every scenario in the project, made by whoever adds them (front end, workbook reader – a row copied in Excel with its id kept, or with it cleared, gets a new one), so an id names one line across the project. Ids are kept when a scenario is copied, so "Copy to…" of a line replaces the line with the same id in the target, or adds it. The schema 2 upgrade renumbers a scenario's own line whose id another scenario already uses for a different line (schema 2 numbered each scenario's own lines from own-1). A scenario has at most 1,000 lines. Reading a line keeps only the fields its frequency uses, so a stale interval or rate never survives a save. A monthly or yearly line's amount is in the dollars of its first year (blank – the start year).
- Schema 3 (v1.6) – every scenario holds `facts` (the old baseline's fields); a project has no baseline, and an adoption no frozen copy. `upgrade.py` upgrades older files as they are read: schema 1's lines become once lines `line-1…` and a non-zero operating figure a yearly line `operating`, as schema 2 did; schema 2 gives each scenario the baseline with its changes applied (an adopted plan, its frozen baseline, its changes applied again – which changes nothing), so every figure is the same, and a project with no scenarios gets "Current dues" (rate mode from the current dues, 0% increase). Saving writes schema 3.
- Each scenario is complete in itself (spec 3, v1.6) – nothing is shared between scenarios. A new scenario is a copy of another (`startFrom` – every input, not the name, adoption or timestamps) or blank from the server. A fact later true for several is copied with "Copy to…" (spec 7.2) – a figure with its source note (the target's note is cleared when the copy has none; a horizon year reshapes the target's tables), an expense line by id, or the Fully Funded Balance table (this scenario's years over the target's, years only the target has kept). The dialog lists every other scenario with an All box; adopted plans are shown but cannot be chosen. One save carries every target.
- Workbook scenario inputs – below each Plan sheet's charts are its facts and assumptions (typed, blue, each with its source note), its Fully Funded Balance (every year it holds, so years beyond the horizon survive a re-import) and its expense table – every line with its year formulas, three spare rows, and the operating and reserve totals as SUMIF over those rows by frequency, which the Plan rows pull. Formulas in a row with a blank frequency give 0. The vote formula uses nested IF, not AND, because LibreOffice evaluates every argument of AND.
- Compare with different horizons (spec 7.4) – labels name calendar years only when every shown scenario shares the horizon, otherwise "year 4", "whole projection", "the projection"; a measure a short scenario cannot have is a dash; the by-year tables run over every year any scenario covers. The Charts page gives stacked charts one year axis over all those years.
- Adopted plans (spec 5.2) – `Scenario.adoption` holds the date as entered, a note and an adoption order (`sequence`; the highest is current, whatever its date); the plan's own inputs are its record, so nothing is frozen separately. Only `POST …/adopt` and `POST …/unadopt` change adoptions; a save that would change, rename, delete, adopt or un-adopt a plan is refused (`ReadOnly`, 409). In the workbook an adopted plan's sheet shows its date, note and order below the reserve total and is protected without a password as a reminder. Adopt waits until the last edit is saved, and the screens never save an adopted plan; "Copy to…" never chooses one. An adoption note is at most 2,000 characters, the order 1–10,000 and the date YYYY-MM-DD, wherever it comes from. A project is never written larger than the 5 MB the store reads back.
### Front-end choices

- A scenario's screens (spec 7.2) – a layout route (`ScenarioLayout`) that stays mounted across Results, Facts and assumptions, Expenses, Fully Funded Balance, Dues and Special assessments, holding one form; the index lists them under Scenarios while a scenario is open. Every edit saves itself (`useAutosave`) 0.6 s after typing stops – a value becoming usable waits too, so "Plan" on the way to "Plan B" is never saved – and anything unsaved goes when the screen closes; closing the tab with an edit still waiting asks first. `ProjectLayout` loads the project once for all its screens and holds one save queue (`useProject().save(build)` builds from the latest saved project, `act` for adopt and un-adopt), so a screen opened while another's last edit is saving sees it. A save refused because another came first (409) reloads the project and is made once more on it. Adopt saves the last edit first; a form is remounted when it is adopted or un-adopted. Copy to… waits while an entry is not usable. Nothing saves while an entry is not a usable number or year, or the name is blank or another scenario's; the status beside the title says so, and leaving a screen with such an entry asks first (the entry would be lost). A rename moves the address without remounting the form. Leaving after a failed save asks first. A deleted scenario is never saved back by a last pending edit. The inputs screens show key results beside them (above, for the wide expense table). The project's name and notes save the same way on Scenarios.
- A field holding text that is not a usable number or year is never saved as its last good value – the scenario lists it and does not save until it is fixed. Money inputs show thousands separators once you leave the field.
- Changing the horizon reshapes the scenario's tables only once it is 5–30 years, and never discards an entry; typed dues are stretched to a new horizon with the nearest figure (`withHorizon`).
- A project's screens (spec 7.1) – an index on the left with Scenarios (the list – adopted plan first, then working scenarios, then earlier plans – and the project's name and notes), Compare, Charts, Export; the project address opens Scenarios. Opening a scenario adds its own screens under Scenarios.
- "Meets target?" shows yes in green and no plainly – not reaching the target is normal for years and is not an alarm.
- Starting a scenario (spec 7.2) is the new-scenario screen – "Start from" a blank scenario or any scenario (`?from=<name>`, changed in place), a name (suggested "<name> – copy"), then Create, which saves it and opens it – a blank one on Facts and assumptions, a copy on Results. "Copy as a new scenario" on a scenario goes there with `?from=`.
### Engine choices the spec leaves open

- Dues modes – the UI offers the spec's three (section 5); the engine has two. `EXPLICIT` is mode a; `RATE` is mode b, and mode c when `overrides` is non-empty.
- `needs_vote` compares the first year's dues with the scenario's current dues. The dues-jump rule is skipped when the prior year's dues are 0 (no percentage exists). A rise of exactly the limit needs no vote.
- Percent funded is 0 when next year's FFB is 0, matching the reference workbook's `IF(FFB=0,0,…)` guard.
- `shortfall_years` (count of operating-shortfall years) is an extra summary measure alongside the section 6 list, feeding the Compare view.
- `dues_y9`, `balance_y9` and `pf_y9` are `None` when the horizon is shorter than 9 years.
- Expense lines and explicit dues outside the horizon are kept and ignored, not errors – shortening the horizon must never discard data. Pinned dues and assessments outside the horizon are errors, since they belong to a scenario's intent for those years.
- An expense line's year or last year must fall within 50 years of the horizon (start − 50 to end + 50) – further out is a typo, and growth over that span would overflow. Within that window, lines outside the horizon are kept and ignored as above.
- The expense base year must fall between 50 years before the start year and the end year; a line dated before the base year is deflated by the same formula.
- The percent-funded target must be above 0% and at most 100%.
- A governance limit that is missing or `null` in a project file means no limit, and is written back as `null`. The spec's 20% / 5% defaults are what a new project starts with.
- The engine runs under its own decimal context (28 digits, half-even); a caller's context cannot change its figures.

## Agents – when to invoke

- **code-reviewer** – before every commit to `main`. Blocking findings must be fixed first.
- **security-reviewer** – before each release, and on any change touching file I/O, import/export, dependencies, the local server, or anything that could carry real data into this repo.
- **documentation-writer** – when a feature is complete and before each release. A release is not done until it passes.

## Working method

Write the failing test first. Commit after each green test run; one concern per commit. Run the code-reviewer (and the security-reviewer where it applies) before committing, fix blocking findings, and record any new decision under Stack decisions.
