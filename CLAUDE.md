# HOAForecaster

The specification is [HOAForecaster_REQUIREMENTS.md](HOAForecaster_REQUIREMENTS.md). Read it before changing behaviour; cite its section numbers in reviews and commit bodies.

## Public code, private data

This repository is public. Never commit a real association's name, figures, people, documents or workbook – not in code, tests, fixtures, comments, commit messages or docs. Real data lives in the private sibling repository `HOAForecaster-data` (section 8.1). Public tests use the fictional demo project in `demo/`.

## Layout

- `src/hoa_engine/` – the calculation engine (section 6). Pure Python, no I/O, `Decimal` throughout. `run(scenario)` is the only entry point – a scenario runs on the `Facts` that `Project.runnable` gives it (the project's, or an adopted plan's frozen copy). `model.py` also holds `Project`, `ExpenseSet` and its functions, and the JSON project format; `upgrade.py` turns schema 1, 2 and 3 files into schema 4; `dues.py` also holds `rebase_dues`.
- `src/hoa_workbook/` – Excel export and re-import (sections 7.1, 7.6). `layout.py` is the single source for sheet names, rows and labels, shared by `export.py` (writer) and `read.py` (reader); `charts.py` builds the native charts. It imports only `hoa_engine.model` and `hoa_engine.validate` – never the engine – so its formulas stay an independent check on the engine (enforced by `tests/workbook/test_independence.py`).
- `src/hoa_store/` – project storage (section 8): one JSON file per project in the data folder, trash, the backup and upgrade notes of a file upgraded from an older schema, adopting and un-adopting, export/import of project files, first-run demo seeding. Every error is a `StoreError` with a plain-language message.
- `src/hoa_app/` – the local server (sections 7, 8, 10.1). `api.py` is the FastAPI app – the JSON API under `/api/` and the built front end from `web/dist`; `__main__.py` is the `hoaforecaster` launcher; `lock.py` keeps one app per data folder.
- `web/` – the screens (section 7), Vite + React + TypeScript, built into `web/dist` and served by `hoa_app`. `src/api.ts` is the only code that talks to the server; `src/decimal.ts` keeps money as exact decimal strings (numbers only for display and charts); `src/pages/` are the screens – `ScenarioScreens.tsx` is a scenario's layout (one form, autosave, live results) and its screens – Results, Dues, Special assessments, and an adopted plan's read-only facts screens – and the facts, expenses and Fully Funded Balance screens both layouts share through `FactsContext`; `ProjectInputs.tsx` is the project's facts screens' layout (one form for the project's facts, autosave, every scenario's key results, the expense sets panel); `src/template.ts` holds the expense set helpers (`expensesOf`, `withExpenses`, `sameExpenses`); `src/App.tsx` exports the `routes`; `src/scale.ts` mirrors `charts.py`'s shared grid. Tests – `npm test` (logic, components, and the app's own routes driven against a mocked API).
- `tests/engine/` – unit tests and the section 9 acceptance tests; 100% coverage of `hoa_engine` is enforced. `test_project.py` covers the schema 4 file, expense sets and the schema 3 upgrade of `fixtures/demo_schema3.json` (the demo as it was at v1.9). `tests/workbook/` – export recalculates in LibreOffice to the engine's figures, export → import round trip, Excel open check (Windows with Excel), bad-file handling. `tests/store/` – storage, including concurrent saves and hostile files. `tests/compare.py` – the engine-vs-workbook comparison.
- `demo/fixtures/` – the fictional project (`project.json`), its exported workbook (`reference.xlsx`) and the figures LibreOffice computed from it (`expected.json`). Regenerate with `uv run python demo/build_reference_workbook.py` after changing the demo project or the exporter's formulas; `expected.json` changing means a formula changed.
- `tools/recalc.py` – LibreOffice headless recalculation and formula-error scan. `tools/extract_expected.py` – reads expected figures out of any workbook in the reference layout. `tools/excel_check.ps1` – opens a workbook in real Excel and reports any repair.

## Commands

```
uv sync                                     # install
uv run hoaforecaster                        # start the app – builds web/dist with npm first if it is missing
uv run pytest --cov                         # tests; add HOA_PRIVATE_DIR=../HOAForecaster-data for the private set
uv run ruff check . && uv run ruff format --check .
uv run mypy
cd web && npm ci                            # front-end packages (exact pins, lockfile)
cd web && npm test && npm run lint && npx tsc --noEmit
cd web && npm run build                     # after changing web/src – a running server lists dist files at start-up, so restart it
```

`git config core.hooksPath .githooks` once per clone turns on the pre-commit checks – the real-data guard (deny-list at `../HOAForecaster-data/denylist.txt`, or `$HOA_PRIVATE_DIR`), ruff, mypy, and the front end's types, lint and tests.

## Stack decisions

- Python FastAPI backend + React/TypeScript front end (section 11, decided in v1.2). Engine and Excel exporter are both Python.
- `uv` for the Python environment; Python ≥ 3.12.
- Money and rates are `Decimal` in memory and decimal strings in JSON; floats are refused on load.
- Dues rounding applies only to grown dues, each year rounded half-up from the unrounded growth; typed and pinned values are used as typed.
- Expected figures always come from a spreadsheet recalculated by Excel or LibreOffice, never from the engine.
- Export – sheets in the order Method, Project (the association's name and notes, then the project's facts and assumptions), Expenses (the set the expenses came from, for information, then the Fully Funded Balance and the expense table), Compare, Charts, then one per scenario. Scenario sheets are named from the scenario, cleaned to a legal, unique name (31 UTF-16 units, no trailing apostrophe); the full name is in cell A1. Dues settings sit below the table; the rounding cell drives the dues formulas (a dropdown), while the dues mode is set in the app because it decides which cells hold formulas. Special assessments are a list, one row each with spare rows, summed into the year row by SUMIF – so installments and notes survive a re-import. Exporting a scenario with problems is refused, naming it, and so is any export while the project's facts have problems (the Project and Expenses sheets carry them whichever scenarios are chosen).
- User text is always written as text, and text starting with = + - @ also gets Excel's quote prefix so it stays text when edited or saved as CSV. Control characters (other than tab, newline and return) are refused in every text field when a project is read.
- Import (`read.py`) reads only the export layout. A v2.0 workbook gives the project's facts from the Project and Expenses sheets and an adopted plan's from below its charts (an adopted plan's sheet without them is refused); it holds no expense sets, so the project comes back with none, its expenses from no set and adopted plans' set record cleared. A v1.6–v1.9 workbook (a Project sheet with only the name and notes, each Plan sheet with its own facts below its charts, no Expenses sheet) is read as a schema 3 project and upgraded – its scenarios' different expenses kept as sets, but without the upgrade notes; a scenario sheet named Expenses in one is still a scenario. A workbook in the layout before v1.6 (Inputs and Expenses sheets, no Project sheet) is refused with a plain message – its project file still imports. Section 7.1a (CSV of expenses and FFB) and 7.1b (the original reference workbook, with its partial first year) are still open; the private repo's `fixtures/make_project.py` does 7.1b as a one-off. A re-import is identical to the exported project except that numbers pass through Excel's doubles (about 15 significant digits). Each label is looked for only in its own part of a sheet (Plan rows from the top, the scenario's blocks each below the one before, totals as the last row with the label), so an expense or note worded like a label never stands in for it. Start and end years are checked as soon as they are read, before any year is walked. An expense row without its year formulas is refused rather than read, because the sheet's own totals would leave it out; a formula typed over a fact or Fully Funded Balance figure is refused.
- Import limits – 20 MB file, 20 MB unpacked, 100:1 compression per part, 2,000 rows by 200 columns per sheet; defusedxml must be active. Imported projects are validated before they are returned. A project holds at most 200 scenarios and 200 expense sets (a set's name at most 100 characters); the schema 2 upgrade refuses more than 1,000 baseline lines or line changes, and more than 50,000 lines written in all (each scenario gets its own copy of the baseline's – a small crafted file must not grow into a huge one). Project files and workbooks are parsed off the server's event loop.
- Two environment variables, never interchangeable – `HOA_DATA_DIR` is the app's own data folder (default the per-user application data folder, `%APPDATA%\HOAForecaster` on Windows); `HOA_PRIVATE_DIR` is the private data repository, used only by the private acceptance tests and the commit guard. The spec's "bundled demo folder" default became the app data folder with the demo copied in on first run, so the app never writes into the repo.
- Storage – `<data>/projects/<id>.json`, `<data>/trash/<id>.json` and `<data>/backups/<id>.json` (a project file as it was before its schema upgrade; deleting the project moves it to `<data>/trash/<id>.before-upgrade.json`). Ids are 12 hex characters made by the server; user text never becomes a file name. Saves are atomic, serialised by a lock and carry a `revision`; a save names the revision it started from and is refused if another save came first. There are no drafts – every edit is saved as it is made (spec 7.2); a `drafts` folder left by an older version is ignored. Delete moves to the trash folder (no restore in the app yet). The demo is copied in only when the projects folder does not yet exist, so a deleted demo stays deleted.
- Timestamps – the project, each scenario and each expense set (`set_times`) have created and modified times (spec section 3); a set is identified by its name under the same rename rule as a scenario. A scenario is identified by its name; a save that swaps exactly one name for another is a rename and keeps that scenario's history, while two renames in one save start new histories. Export project carries the timestamps, not the id or revision, and its import keeps valid ones; the Excel workbook carries no timestamps, so a re-imported workbook starts new ones.
- Server – binds to 127.0.0.1 only (the launcher has no host option). Every `/api/` call must carry the per-launch token in `X-HOA-Token`; the token is generated at start-up and written into `index.html` as it is served (placeholder `__HOA_TOKEN__`), so other web pages cannot call the API (CSRF). A page opened before a restart holds the old token: on the exact 403 "this request did not come from HOAForecaster" it re-reads the token from `/` (only the app's own page can read it – no CORS, the Host check, `frame-ancestors 'none'`) and resends that request once, so an edit is still saved. The Host header must be `127.0.0.1` or `localhost` (DNS rebinding). Bodies are capped at 21 MB before they are read, and JSON bodies are refused over 5 MB. Front-end files are served only from a list made at start-up – request text never reaches the file system. The page itself is never cached. Uploads are read in memory, never spooled to the temp folder. Errors are `{"message", "problems"}` in plain language; nothing returns a traceback. The front end gets a strict Content-Security-Policy.
- Restarting (the header's Restart button) – `uv run hoaforecaster` is a small supervisor that runs the server as a child process (`--serve`, hidden). `POST /api/restart` (token-guarded) answers first, then stops that server, which exits with code 75 – or ends itself after 5 seconds if it has not stopped. The supervisor starts a new server only once the old process has ended and the port is free (it waits up to 10 seconds, then gives up rather than start a second server), rebuilding the screens first if they changed; the browser opens only on the first start, and the page waits for a page carrying a new token before it reloads. Without the supervisor (tests, `--serve`), `/api/about` says `can_restart: false` and the button is hidden.
- Starting again while running – the running copy is its launcher (the supervisor), not only its server. For its whole life the launcher holds `<data>/.launcher.lock` and keeps `<data>/.running.json` (its pid, port and a stop key of its own; written whole through a new file opened exclusively, never following a link; at most 4 KB is ever read back, and anything damaged, nested or out of range is no record) – removed when it ends, only if still its own. Each server it starts gets the key through its stdin (`--stop-key-on-stdin`), never its command line. A new launch that cannot take the launcher lock posts the key to `POST /api/stop` on 127.0.0.1 – through an opener with proxies off and redirects refused, so neither a proxy nor a redirect ever carries the key – asking again for up to 2 minutes while that copy is still building or between servers. The guard checks the stop key, never the page token, so nothing the page runs can stop the server; `create_app` takes the key and the stop action together or neither. The old server answers, stops (stopping for good wins over a restart asked at the same moment), and ends itself after 5 seconds if it has not; its launcher then exits 0. The new launch waits up to 15 seconds for the launcher lock and the old port, then starts as usual – or says the running copy could not be stopped and starts nothing beside it. Ctrl+C while waiting ends quietly. If the record cannot be written the app still starts and says a relaunch will not stop it. A copy started before this version holds no launcher lock and cannot be stopped this way. `HOAForecaster.bat` pauses only when the app stopped with a non-zero code, so a replaced copy's window closes.
- Problems are plain sentences that name the field in words ("the 2031 expense 'Gate' cannot be negative"); the editors show them as a list. Field keys for highlighting the exact input are a possible later change to `validate.py`.
- New projects and scenarios – `POST /api/projects` with only a name builds a project with `blank_facts` (the spec's defaults – next year, 14 years, 3% inflation, 2% interest, a 70% target, the 20% and 5% vote limits, amounts zero) and one blank scenario ("First scenario"); `GET /api/blank-scenario?name=&dues=` gives a blank funding plan for the new-scenario screen – dues from the project's current dues rising 3% a year, no assessments, whole-dollar rounding (`hoa_app/template.py`), so the defaults live in Python once.
- Dependencies resolve only from releases old enough for a bad one to be caught – Python a week (`[tool.uv] exclude-newer`), npm two weeks. npm has no rolling setting, so the front end's exact pins and its lockfile are made with `npm install --before=<date two weeks ago>`; do the same whenever packages are added or upgraded.
- Not yet built – trash list and restore, CSV import of the expense and FFB tables (7.1a), importing the original reference workbook from the app (7.1b), choosing the data folder in the app (it is `HOA_DATA_DIR`).
- API results carry money and rates as exact decimal strings; the front end converts to numbers only for display and charts.
- The Charts sheet's shared dollar scale is passed in by the caller from the engine's results, snapped to a grid whose lines coincide with 0–100% in 20% steps.
- Expense lines (spec 4.1) – one list in the project's facts (and one in each adopted plan's frozen copy and each expense set), each line with a `frequency` (`monthly`, `yearly`, `every`, `once`) and an `id` (`[a-z][a-z0-9_-]{0,39}`, unique in its list – lower case and starting with a letter, so a spreadsheet COUNTIF never reads one as a number and two never match by case). A new line on the project's Expenses screen gets the first free `line-N` among the project's lines and every adopted plan's frozen lines; the workbook reader gives a row copied in Excel with its id kept, or with it cleared, the first `line-N` no expense table of the workbook uses. Ids are kept when the expenses are saved as a set and loaded again. A list has at most 1,000 lines. Reading a line keeps only the fields its frequency uses, so a stale interval or rate never survives a save. A monthly or yearly line's amount is in the dollars of its first year (blank – the start year).
- Schema 4 (v2.0) – the project holds `facts`, `expense_sets`, `expenses_from` (the set the expenses were loaded from, which must be a saved set) and `expenses_edited`; a scenario's `facts` is `null` except on an adopted plan, which must have them (`check_project`). `upgrade_v3_project` reads schema 3 (v1.6–v1.9, every scenario with its own facts) – the project takes the facts of its first scenario that is not adopted (the first scenario if all are); each different set of scenario expenses (`same_set`, adopted plans' included) becomes a set "Expenses from <first scenario>", cut to 100 characters and numbered to stay unique, recording that scenario's reserve inflation, and the project's expenses came from its first scenario's set; adopted plans keep their facts, with `adoption.expenses_from` naming their set; every other scenario drops its facts after `rebase_dues` carries its dues onto the project's start year; no scenarios gives `blank_facts` for next year. `read_project(d, report=True)` also returns one sentence per scenario whose facts differed – what differed, whether its figures change (running it before and after), whether it now matches another scenario's funding exactly, and the set its expenses went to. Schema 1 and 2 files go through their upgrades to schema 3 first (schema 1's lines become once lines `line-1…` and a non-zero operating figure a yearly line `operating`; schema 2 gives each scenario the baseline with its changes applied, an adopted plan its frozen baseline). Saving writes schema 4.
- The project holds the facts (spec 3, v2.0) – the facts and assumptions, the expenses and the Fully Funded Balance are the project's, shared by every scenario but an adopted plan; a scenario holds only its funding – dues, assessments, rounding, name and description. This reverses v1.6, where every scenario held every input (and "Copy to…" moved facts between them – gone). `Project.runnable(s)` gives a scenario the project's facts when its own are `None`; the server (`_results`, `dollar_axis`, `/api/run` with the project's facts sent alongside, `/api/run-project` for the facts screens, which also returns the project's own facts' problems and Fully Funded Balance), the exporter and the upgrade all run scenarios through it. A new scenario is a copy of another's funding (`startFrom` – not the name, adoption or timestamps) or blank from the server; it always uses the project's facts, even when copied from an adopted plan, whose grown dues are then carried onto the project's start year (the screen takes what the plan's results charged in that year).
- Worked-out Fully Funded Balance (spec 4.2, v1.7) – `Facts.ffb_from_lines` chooses it for the project's facts (an adopted plan's frozen copy keeps its own, and an expense set carries it); the typed `ffb` is kept for switching back and needs no years while worked out. A component's life is an every-few-years line's interval, or a once line's optional `useful_life` (read only for once lines; moving a line between those kinds carries one into the other). `engine.line_ffb` – cost in year-Y dollars × age ÷ life, remaining life `(next − Y) mod life` (Python's and Excel's MOD both take the divisor's sign, so a replaced component keeps ageing on its cycle), a component not yet in service counts 0, an every-few-years line retires after its last year, a nominal amount is moved from the line's own (first) year, since every occurrence grows from it (v1.9). `useful_life` and `ffb_from_lines` are optional fields of schema 3 (older files read as no life, typed figures), so the schema did not move. A typed useful life becomes an every-few-years interval when a line changes kind, but a default interval never becomes a useful life. The API result carries `ffb`. `ScenarioResult.ffb` carries the figures start to end + 1 for the screen. In the workbook each FFB cell is one SUMPRODUCT over the Expenses sheet's expense rows (an adopted plan's, over its own rows below its charts), a mode row below says which is used (set in the app), and the typed figures sit in a kept row; in worked-out mode a figure typed over a formula is refused, and a sheet from before v1.7 (no mode row) reads as typed.
- Workbook facts and expenses (v2.0) – the Project sheet holds the project's facts and assumptions below the name and notes (typed, blue, each with its source note in a column beside it), and the Expenses sheet its Fully Funded Balance (every year it holds, so years beyond the horizon survive a re-import) and its expense table – every line with its year formulas, three spare rows, and the operating and reserve totals as SUMIF over those rows by frequency. Every Plan sheet's formulas read those sheets, so a fact changed in Excel changes every scenario; an adopted plan's sheet carries its frozen facts, Fully Funded Balance and expenses below its charts (headed "This scenario's …") and its formulas read those. Formulas in a row with a blank frequency give 0. The vote formula uses nested IF, not AND, because LibreOffice evaluates every argument of AND.
- Compare with different horizons (spec 7.4) – labels name calendar years only when every shown scenario shares the horizon, otherwise "year 4", "whole projection", "the projection"; a measure a short scenario cannot have is a dash; the by-year tables run over every year any scenario covers. The Charts page gives stacked charts one year axis over all those years.
- Adopted plans (spec 5.2) – `Scenario.adoption` holds the date as entered, a note, an adoption order (`sequence`; the highest is current, whatever its date) and `expenses_from` / `expenses_edited`, a record of the set the project's expenses came from when it was adopted (it need not still be saved). Adopting (`store.adopt`) gives the plan a frozen copy of the project's facts as they are; un-adopting (`store.unadopt`, the current plan only) drops the copy and carries its dues onto the project's start year with `rebase_dues`, so its figures change if the project's facts have. Only `POST …/adopt` and `POST …/unadopt` change adoptions; a save that would change, rename, delete, adopt or un-adopt a plan is refused (`ReadOnly`, 409) – loading a set never touches one. An adopted plan's frozen expenses can be saved as an expense set from its Expenses tab, which changes the project, not the plan. In the workbook an adopted plan's sheet shows its date, note and order below the reserve total and is protected without a password as a reminder. Adopt waits until the last edit is saved, and the screens never save an adopted plan. An adoption note is at most 2,000 characters, the order 1–10,000 and the date YYYY-MM-DD, wherever it comes from. A project is never written larger than the 5 MB the store reads back.
- Expense sets (spec 4.3, v2.0) – `ExpenseSet` holds a copy of the expense parts of a set of facts – lines, base year, `ffb`, `ffb_from_lines`, the source notes on `ffb` and `expense_base_year` – and `saved_inflation`. `expenses_of` makes one, writing a monthly or yearly line's blank first year as the start year, so a set means the same figures whenever it is loaded (the project's own facts keep the blank). `with_expenses` loads one – every other fact as it was, the reserve rate included, and the typed Fully Funded Balance years the set lacks kept (amended after the math audit). `same_set` compares lines by id in any order, ignoring the name and saved inflation. Saving, loading, renaming and deleting sets are ordinary project saves made by the Expenses screen; its TypeScript twins (`expensesOf`, `withExpenses`, `sameExpenses` in `template.ts`) must stay in step with the Python. Any change to the expenses after a load marks them edited (`expenses_edited`). Deleting the loaded set leaves the expenses, from no set.
- Upgrading a stored project (spec 8.2) – `ProjectStore.get` saves a file of an older schema in schema 4 the first time it is opened, after copying the original to `<data>/backups/<id>.json` (once – an existing backup is kept), and stores the upgrade's sentences in the file's `upgrade_notes` (at most 200 of 2,000 characters; a damaged list reads as none, a damaged note is left out). A file too large to save in schema 4 opens as it is, unsaved; two requests opening the same old file upgrade it once. The project's screens show them in a panel until `POST /api/projects/<id>/dismiss-notes` clears them. An imported older project file is upgraded with its notes too, but without a backup (the user still has the file). Export project leaves the notes out.

### Front-end choices

- Look (v1.9 look-and-feel pass, in the style of online-banking screens) – white pages, navy pill buttons (the main action filled), a thin red mark by the name, link-blue toolbar actions with an icon ("Download CSV ⤓"), tables with bold headers, thin rules and striped rows (the stripe on the row, so a cell's own colour – an input, a flag – shows over it), soft-shadowed rounded panels. Light unless the header's "Dark screens" switch is on – `theme.ts` sets `data-theme` on the root before the first paint and keeps the choice in the browser (once there are users it becomes a per-user setting there); the screens no longer follow the system's colour scheme. Printing is always light.
- Cards only where things are chosen rather than compared – the project list (a card per project, ordered by a Sort choice: last saved first, name, or most scenarios) and a new scenario's "Start from" (a radio card per choice). Lists that are compared stay tables.
- A scenario's screens (spec 7.2) – a layout route (`ScenarioLayout`) that stays mounted across Results, Dues (which also holds the name and description) and Special assessments – an adopted plan's also its read-only Facts and assumptions, Expenses and Fully Funded Balance, showing its frozen copy – holding one form; they are tabs under the scenario's name. Every edit saves itself (`useAutosave`) 0.6 s after typing stops – a value becoming usable waits too, so "Plan" on the way to "Plan B" is never saved – and anything unsaved goes when the screen closes; closing the tab with an edit still waiting asks first. `ProjectLayout` loads the project once for all its screens and holds one save queue (`useProject().save(build)` builds from the latest saved project, `act` for adopt and un-adopt), so a screen opened while another's last edit is saving sees it. A save refused because another came first (409) reloads the project and is made once more on it. Adopt saves the last edit first; a form is remounted when it is adopted or un-adopted. Nothing saves while an entry is not a usable number or year, or the name is blank or another scenario's; the status beside the title says so, and leaving a screen with such an entry asks first (the entry would be lost). A rename moves the address without remounting the form. Leaving after a failed save asks first. A deleted scenario is never saved back by a last pending edit. Dues and Special assessments show the scenario's key results beside them. The project's name and notes save the same way on Scenarios.
- A field holding text that is not a usable number or year is never saved as its last good value – the scenario lists it and does not save until it is fixed. Money inputs show thousands separators once you leave the field.
- Changing the horizon on the project's Facts and assumptions reshapes its Fully Funded Balance table only once it is 5–30 years (`factsWithHorizon`), and never discards an entry; every scenario's typed dues but an adopted plan's are stretched to the new horizon with the nearest figure (`duesWithHorizon`, in `withProjectFacts`).
- A project's screens (spec 7.1) – a bar across the top with the project's name and Scenarios (the list, in the project's order, and the project's name and notes), Facts and assumptions, Expenses, Fully Funded Balance, Compare, Charts, Export; the project address opens Scenarios. An open scenario's own screens are a row of underlined tabs under its name, its actions to the right of the name. The upgrade notes panel sits above every project screen while there are notes.
- The project's facts screens (spec 7.1, v2.0) – a layout route (`ProjectInputsLayout`) that stays mounted across Facts and assumptions, Expenses and Fully Funded Balance, holding one form for the project's facts that saves itself like a scenario's (`withProjectFacts` marks the expenses edited when they changed since a set was loaded). Beside the inputs (above, on Expenses) a table gives every scenario's key results – the lowest balance and its year, percent funded at the end, the years below the cushion – from `POST /api/run-project` on the facts as typed, debounced; adopted plans are named below it, unchanged. The Expenses screen's Expense set panel names the set the expenses came from and whether they have been edited since, and offers Save as a set…, Save changes to the set (only when edited), and Load…, Rename… and Delete for each saved set. Loading asks first – expenses from no set, whether to save them as a set; edited ones, save the changes, save as a new set or discard – and, when the set's saved inflation differs, offers to switch the project's rate (ticked). Every set action saves the last edit first. Compare names the set above its summary, and the adopted plans shown, which keep their own.
- An every-few-years table numbers its lines and shows each one's later occurrences in the scenario beneath it, read-only (`repeatsOf` – the years and amounts the engine charges, inflated from the base year or flat when already inflated), behind a Show repeats box that starts on. Tables longer than 70% of the window scroll in their own box with the header row held (and the corner and first column, on Results and Compare); printing shows them whole.
- The Results labels name the figures the scenario runs on – "Below cushion ($75,000)?", "Meets target (60.0% funded)?" (the target is a share of each year's Fully Funded Balance, so no one dollar figure); the CSV uses the same labels.
- Results (spec 7.3) – the Plan table on screen is a headline table (dues, assessment, operating and reserve expenses, ending balance, percent funded, owner cost of dues for the year, below cushion – `headline` on its row; an owner's dues and assessment on separate lines, their total in the details) and a details table with the rest in the spec's order, each a collapsible `<details>` (headline open, details closed); its CSV holds every row in the spec's order. Printing opens every collapsed section. Collapsible sections carry their title as plain text in the `<summary>` (a summary is a button, so a heading inside it loses its role).
- Sortable tables – `components/sort.tsx` `useSort`: a header click sorts what is shown, never the saved order (so the workbook and the CSV of an editable table keep theirs; a CSV of a read-only table follows the screen); a second click reverses, a third restores; blanks last, except a yearless expense sorts as its start year. In an editable table (`keyOf` given) the order is fixed at the click, so a row being typed in never moves, and pasting a column fills down in the order shown. Sortable – scenarios, Compare's by-year tables, the four expense tables, both Fully Funded Balance tables, dues by year, special assessments. Not sorted – the expense sets list and the key-results table on the facts screens. Not sortable – the Results plan table, Facts, Compare's summary (rows are measures in a set order). "Sort by year" on an expense table still changes the saved order.
- Scenario order (spec 7.1, 7.4) – the order of `project.scenarios` is the board's, set by Move up / Move down on Scenarios (disabled while a header sorts the table) or the arrows in Compare's column headers (`moveScenario` – past the neighbour shown, so past any scenarios Compare hides); each move is a project save. Compare, Charts and Export show the chosen scenarios in that order whatever order they were ticked in, and Compare's first column is the one differences are from. Moving a scenario is not a change to it, so an adopted plan can be moved and no scenario's modified time changes.
- "Meets target?" shows yes in green and no plainly – not reaching the target is normal for years and is not an alarm.
- Compare's extra cost (spec 7.4) – a "Current dues per unit per month – what extra cost is measured against" row sits above the extra-cost rows, whose labels name the dues when every shown scenario shares them ("Extra cost per unit over today's $560 a month, 2027–2030"), otherwise "over each scenario's current dues"; a note under the summary says what extra cost is. The workbook's Compare sheet keeps its "Extra cost vs current dues" labels (`tools/extract_expected.py` reads them).
- Starting a scenario (spec 7.2) is the new-scenario screen – "Start from" a blank scenario or any scenario (`?from=<name>`, changed in place), a name (suggested "<name> – copy"), then Create, which saves it and opens it – a blank one on Dues, a copy on Results. A copy takes the dues path, assessments, rounding and description. "Copy as a new scenario" on a scenario goes there with `?from=`.
### Engine choices the spec leaves open

- Yearly dues increases by period (spec 5.1, v1.8) – `DuesPath.increases`, each `Increase(rate, first_year, last_year)` with None for the start or end; a period's years are the years raised by its rate, so the start year is never in one. Every year after the start must be in exactly one (`validate._increases` names gaps and overlaps as runs of years, and a period ending before it starts or naming a year outside the scenario). Growth runs a power per run of equal rates, so a single increase gives exactly what `annual_increase` did; a file with `annual_increase` and no `increases` reads as one period. At most 100 increases. The Dues screen's Add never changes a row already there: the new one starts the year after the last one's to year, at its rate, to the end – or blank when the last runs to the end, its overlap listed until set. In the workbook each Plan sheet has a yearly increases list below the assessments (From, To, Increase, three spare rows; blank for typed dues), each year's rate a SUMPRODUCT over the rows covering it and the grown dues `prior × (1 + that year's rate)`; the reader takes the rows the first year's formula spans, refuses a filled row outside them or a rate typed over a formula, and reads a sheet from before periods by its old single-rate label.
- Dues modes – the UI offers the spec's three (section 5); the engine has two. `EXPLICIT` is mode a; `RATE` is mode b, and mode c when `overrides` is non-empty.
- `needs_vote` compares the first year's dues with the current dues of the facts the scenario runs on. The dues-jump rule is skipped when the prior year's dues are 0 (no percentage exists). A rise of exactly the limit needs no vote.
- Percent funded is 0 when next year's FFB is 0, matching the reference workbook's `IF(FFB=0,0,…)` guard.
- Interest is earned only on a positive starting balance – none is earned or charged while the balance is negative (spec 6, v1.9; the fund cannot borrow at its savings rate, and a negative balance is already flagged).
- An already-inflated (nominal) every-few-years line is in its first year's dollars, each later occurrence grown from it at reserve inflation (spec 4.1, v1.9) – in the engine, the workbook's expense and FFB formulas and the screen's repeats list. An operating line with a later first year is priced in that year's dollars and never grown before it starts, and reserve lines have no rate of their own – both confirmed by the board after the first math audit.
- `shortfall_years` (count of operating-shortfall years) is an extra summary measure alongside the section 6 list, feeding the Compare view.
- `dues_y9`, `balance_y9` and `pf_y9` are `None` when the horizon is shorter than 9 years.
- Expense lines and explicit dues outside the horizon are kept and ignored, not errors – shortening the horizon must never discard data. Pinned dues and assessments outside the horizon are errors, since they belong to a scenario's intent for those years.
- An expense line's year or last year must fall within 50 years of the horizon (start − 50 to end + 50) – further out is a typo, and growth over that span would overflow. Within that window, lines outside the horizon are kept and ignored as above.
- The expense base year must fall between 50 years before the start year and the end year; a line dated before the base year is deflated by the same formula.
- The percent-funded target must be above 0% and at most 100%.
- A governance limit that is missing or `null` in a project file means no limit, and is written back as `null`. The spec's 20% / 5% defaults are what a new project starts with.
- The engine runs under its own decimal context (28 digits, half-even); a caller's context cannot change its figures.
- A scenario without facts cannot run – `validate_run` gives the one problem "<name> has no facts to run on"; callers use `Project.runnable`.
- Moving a dues path to a new start year (spec 5, v2.0) – `rebase_dues(scenario, old_facts, start_year)` sets a grown path's first-year value to what it charged in that year, rounded as the path rounds; pinned years, periods, explicit dues and assessments keep their years (outside the horizon they are problems or ignored, as usual). It does nothing for typed dues, an unmoved start, a new start outside the old horizon, or a path with problems on its old horizon. Used by un-adopt and the schema 3 upgrade; the new-scenario screen does the same from the run results.

## Agents – when to invoke

- **code-reviewer** – before every commit to `main`. Blocking findings must be fixed first.
- **security-reviewer** – before each release, and on any change touching file I/O, import/export, dependencies, the local server, or anything that could carry real data into this repo.
- **documentation-writer** – when a feature is complete and before each release. A release is not done until it passes.
- **math-auditor** – on any change to `src/hoa_engine/`, the workbook's formulas or a figure the screens work out themselves (`repeatsOf`), and before each release – launched in parallel with the code-reviewer and any other reviewers, never after them. It works examples by hand from the spec before reading the code, because the engine and the workbook share one author and a shared misreading passes every test. Its disagreements become section 9 acceptance tests; its questions go to Gregory.

## Working method

Write the failing test first. Commit after each green test run; one concern per commit. Run the code-reviewer before committing – with the security-reviewer and the math-auditor alongside it, in parallel, where they apply, fix blocking findings, and record any new decision under Stack decisions.
